# Goal-Driven Acceptance Contract

This contract defines the user-visible workflows that prove a goal-driven run
has achieved its original goal without weakening existing static graph
behavior. It is an acceptance contract for CLI, worker, and visualizer behavior;
the lower-level planner response shape remains in
[`planner-output-schema.md`](planner-output-schema.md), and safety boundaries
remain in
[`planning-safety-and-approval.md`](planning-safety-and-approval.md).

## Artifact Boundaries

Goal-driven workflows use three distinct artifacts:

- Generated graph artifact: the validated `plan.graph.json`-shaped file written
  by `plan --goal`. It may be written to an explicit `--graph` path or to the
  default `runs/goals/<timestamp>-<safe-goal-slug>/plan.graph.json` path. This
  artifact is durable graph state.
- Execution graph: the graph file a scheduler command, worker, renderer, or
  visualizer is currently operating on. It may be hand-authored, generated by
  `plan --goal`, or copied from a prior run. Workers execute only against this
  validated graph file, never against raw planner text.
- Optional debug JSON: planner request/response dumps, dry-run command JSON,
  validation diagnostics, or proposal previews. These are inspectable support
  artifacts. They are not graph state, are not replay handles, and must not
  make any node claimable unless their contents are later validated and written
  to an execution graph.

## Compatibility Note

The original generated-goal shape `ROOT -> PLAN` remains supported as a minimal
generated graph. It is not the only compatible `plan --goal` output.

`plan --goal` may instead write a decomposed series-parallel graph directly,
such as `ROOT -> [DISCOVER, BUILD, VERIFY]` or a nested mix of `series` and
`parallel` nodes, when the planner can validate that decomposition before the
graph write. Existing operators must therefore rely on the written graph's
`graph.root`, `graph.nodes`, and readiness commands, not on a hard-coded `PLAN`
node id or a fixed `ROOT -> PLAN` topology.

This broader output shape is additive. Existing `ROOT -> PLAN` fixtures,
existing hand-authored `plan.graph.json` files, and existing commands that
select a graph with `--graph`, `PLAN_GRAPH`, or the package-root
`plan.graph.json` fallback remain valid static graph workflows.

## Planner Decisions

Planner decisions are accepted only after scheduler validation:

- Atomic decision: `kind: "task"`. The target remains one claimable unit with
  no planner-created children. In worker-assisted planning, Codex may execute
  this node after the normal claim/start boundary.
- Series decision: `kind: "series"`. The target becomes an ordered parent.
  Readiness exposes the first unfinished child subtree, and later children wait
  for earlier children to finish.
- Parallel decision: `kind: "parallel"`. The target becomes a fanout parent.
  Readiness exposes ready leaves from each unfinished child subtree
  independently, subject to normal lease and status rules.

Empty `series` and `parallel` decisions are invalid. Planner-proposed ids,
titles, metadata, and child topology must be materialized into a valid graph
before they can affect readiness.

## Execution Approval Rule

The scheduler may execute work only when one of these explicit execution
signals is present:

- An operator runs `worker`, `claim` plus `start`, or a visualizer worker-start
  action against an existing validated graph path.
- An operator runs `plan --goal ... --then-run`, which first writes and reloads
  the validated generated graph, then invokes the existing worker runtime.
- Worker-assisted planning is enabled on the execution graph and a worker has
  already claimed/started the target node. `auto-decompose` may apply valid
  series or parallel planner decisions through the normal `decompose` mutation;
  `ask-approval` must block with an inspectable preview instead of mutating
  children.

The scheduler must ask for approval, or stop before execution, when the user
chooses dry-run, plain `plan --goal`, `--plan-only`, visual review without a
worker-start action, or worker planner `mode: "ask-approval"`. Raw planner
output, optional debug JSON, and regenerated proposals are never execution
approval.

## Acceptance Scenarios

### Plan-Only

User-visible workflow:

```bash
node scripts/plan-scheduler.mjs plan --goal "Ship a searchable audit log" --graph /tmp/spg-audit-log/plan.graph.json --plan-only
node scripts/plan-scheduler.mjs summary --graph /tmp/spg-audit-log/plan.graph.json
node scripts/plan-scheduler.mjs ready --graph /tmp/spg-audit-log/plan.graph.json
```

Acceptance:

- The `plan` command reports `mode: "plan-only"`, `written: true`, the graph
  path, validation results, and next commands.
- The generated graph artifact is valid graph JSON and may be either minimal
  `ROOT -> PLAN` or an already decomposed series-parallel graph.
- No worker starts, no workspaces are created, and no node is moved to
  `claimed` or `running` by planning alone.
- `summary` and `ready` operate on the written graph path as ordinary static
  graph commands.

### Approve Before Run

User-visible workflow:

```bash
node scripts/plan-scheduler.mjs plan --goal "Ship a searchable audit log" --graph /tmp/spg-audit-log/plan.graph.json --plan-only
node scripts/plan-scheduler.mjs diagnostics --graph /tmp/spg-audit-log/plan.graph.json
npm run serve -- --graph /tmp/spg-audit-log/plan.graph.json --cwd "$PWD" --port 8787
npm run worker -- --graph /tmp/spg-audit-log/plan.graph.json --session codex-A --once --cwd "$PWD"
```

Acceptance:

- The review commands inspect the saved execution graph and do not reinterpret
  the original goal text.
- Execution starts only after the separate worker command or visualizer
  worker-start action against the saved graph path.
- The worker claims a ready leaf selected from the saved graph. If the graph
  was pre-decomposed, the ready leaf may be a generated child rather than
  `PLAN`.
- Completion is proven by normal graph evidence: terminal `done` status for
  the root or requested subtree, reports, history entries, and summary counts.

### Auto-Decompose

User-visible workflow:

```bash
node scripts/plan-scheduler.mjs plan --goal "Build fixture resume coverage" --graph /tmp/spg-fixture/plan.graph.json --plan-only
npm run worker -- --graph /tmp/spg-fixture/plan.graph.json --session codex-A --once --cwd "$PWD"
node scripts/plan-scheduler.mjs ready --graph /tmp/spg-fixture/plan.graph.json
```

Acceptance:

- Auto-decomposition is active only when the execution graph or worker options
  enable worker planner mode `auto-decompose`.
- For an atomic planner decision, the worker continues with normal Codex
  execution for the claimed node.
- For a valid series or parallel decision, the worker applies the normal
  locked `decompose` mutation, records planner/decomposition history, and does
  not execute Codex for the decomposed parent in that pass.
- The next `ready` output reflects the new graph topology: first unfinished
  child for series, eligible children from each branch for parallel.
- In `ask-approval` mode, the same valid proposal blocks the leased node with
  an inspectable preview and requires an operator-approved `decompose`,
  `reset`, or `fail` action before child work can run.

### Static Graph Replay

User-visible workflow:

```bash
node scripts/plan-scheduler.mjs summary --graph ./plan.graph.json
npm run worker -- --graph ./plan.graph.json --session codex-A --once --cwd "$PWD"
node scripts/plan-scheduler.mjs worker --graph /tmp/spg-audit-log/plan.graph.json --session codex-B --once
```

Acceptance:

- Existing static `plan.graph.json` behavior remains supported. Commands
  without `--goal` never call the goal planner and never create a new graph
  from a goal.
- `--graph` selects the input execution graph for every existing scheduler,
  worker, renderer, and visualizer command; if omitted, the fallback order is
  still `PLAN_GRAPH`, then package-root `plan.graph.json`.
- A generated graph artifact is replayed exactly like a hand-authored graph
  once its path is passed to `summary`, `ready`, `worker`, `serve`,
  `diagnostics`, or recovery commands.
- Re-running `plan --goal` creates a new generated graph artifact by default;
  it is not the resume mechanism for an existing run.
