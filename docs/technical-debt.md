# Technical Debt And Complexity Guardrails

This document records known maintainability tradeoffs and the policy for
containing future complexity. It is intentionally lightweight: the goal is to
make residual risk visible before it turns into reviewer memory or a rewrite
wish list.

Use this with [`architecture.md`](architecture.md), [`testing.md`](testing.md),
and [`quality-bar.md`](quality-bar.md). Architecture owns module boundaries,
testing owns proof strategy, and this document owns when size, coupling, or
dependencies have become debt.

## Debt Register

### Urgent Debt

There is no known urgent maintainability debt at the time of this review.

Urgent means the issue can hide correctness, security, recovery, or public
contract regressions in ordinary work. If urgent debt appears, record it here
with an owner, affected files, required fix, and a test or review gate. Do not
treat the repository as release-ready while urgent debt is unresolved.

### Acceptable Tradeoffs

These are intentional and should not be fixed without a concrete failure mode:

- The scheduler remains filesystem-backed instead of introducing a database.
  Atomic writes, locks, and plain JSON inspection are part of the operating
  model.
- The built `dist/` directory is generated output, not a source-edit location.
  Source changes belong in `scripts/*.ts` and are verified through `npm run
  build`.
- The visualizer is a trusted local operations tool. Do not add hosted,
  multi-tenant, or public-internet assumptions without a new security design.
- The test suite emphasizes behavior and contract evidence over line coverage
  percentages. Add coverage tooling only when it catches a real class of missed
  behavior or becomes part of the release bar.
- Small compatibility wrappers in `scripts/*.mjs` should stay thin even if they
  look redundant next to built entry points.

## Module Split Policy

Split a module when at least one of these conditions is true:

- The file crosses the review threshold for its role and has more than one
  owner-worthy responsibility.
- A new feature needs tests to import a narrow helper that is hard to reach
  without pulling in unrelated side effects.
- The module starts depending on a higher architecture layer from
  [`architecture.md`](architecture.md).
- The same setup, validation, or rendering pattern is copied three or more
  times.
- A function grows large enough that the happy path, validation, side effects,
  and error handling are no longer easy to review independently.

Default thresholds:

- Source modules: review at about 800 lines, split candidates at about 1,200
  lines unless the file is a deliberate ownership boundary.
- Runtime/UI modules: review at about 1,500 lines and split before 2,000 lines
  when there are independent server, process, and browser concerns.
- Test files: review at about 2,500 lines, split candidates at about 4,000 to
  5,000 lines or when a single failure requires scanning unrelated domains.
- Helper modules: keep them small and specific. A helper module that becomes a
  dumping ground should be split by domain or moved back to its owner.
- Exported symbols: review at about 25 per module, split candidates at about 75,
  and urgent at 200.
- Test cases: review at about 40 per suite, split candidates at about 80, and
  urgent at 140.

When splitting, preserve behavior first:

1. Move code without changing public command, graph, report, visualizer, or
   renderer contracts.
2. Keep side-effect boundaries explicit. Pure helpers may move inward or
   sideways; filesystem, process, network, and HTTP behavior should stay behind
   the documented runtime boundaries.
3. Add or adjust the smallest tests that prove imports, CLI behavior, and public
   output still match.
4. Update `architecture.md` only when ownership or dependency direction changes,
   not for purely mechanical moves.

## Dependency Policy

The project should stay small. Add a runtime dependency only when the standard
library or existing dev tooling would make the implementation substantially
riskier, not merely longer.

Before adding a dependency:

- Prefer built-in Node APIs and existing packages already in `package.json`.
- Confirm the package supports the Node.js LTS majors declared in
  `package.json`, ESM usage, and the repository's TypeScript settings.
- Check that the license is compatible with private/internal distribution.
- Avoid packages with networked postinstall scripts, large transitive trees, or
  broad native bindings unless the feature cannot be delivered safely without
  them.
- Keep production dependencies stricter than dev dependencies. Browser testing
  tools can stay dev-only; scheduler runtime code should remain dependency-light.
- Update `package-lock.json`, tests, docs, and release notes in the same change.

`npm run audit:dependencies` enforces the current policy in release checks:
there must be no production dependencies in `package.json` or the lockfile, all
locked dependency licenses must be allowlisted, and the moderate-level npm
vulnerability audit must pass.

Adding a dependency is justified when it replaces a security-sensitive parser,
protocol implementation, browser automation layer, or other mature domain where
hand-rolled code would create more debt than the dependency. It is not justified
for small argument reshaping, simple graph traversal, string formatting, or
one-off convenience helpers.

## Review Cadence

Review this document during release preparation and whenever a change touches a
large module listed above. If a risk is fixed, remove or downgrade it in the
same change as the code and tests. If a new tradeoff is accepted, record why it
is safe, what would make it urgent, and which existing gate would catch
regressions.
